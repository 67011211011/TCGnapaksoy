# ♛ TCGnapaksoy — ตลาดประมูลการ์ดสะสม

เว็บแอปพัฒนาด้วยภาษา **Go** (`net/http` + `html/template`) และ **SQLite** สมาชิกลงขายการ์ดเป็นการประมูล (พร้อมอัปโหลดรูปการ์ด) สมาชิกคนอื่นเสนอราคาแข่งกัน หมดเวลาแล้วผู้เสนอราคาสูงสุดชนะ ธีมสีดำ-ทอง

> โปรเจกต์เพื่อการศึกษา ไม่มีการชำระเงินจริง ภาพการ์ดตัวอย่าง 5 ใบใน `static/samples/` เป็นลิขสิทธิ์ของเจ้าของลิขสิทธิ์ (©Pokémon / Nintendo / Creatures / GAME FREAK) ใช้เพื่อการศึกษาเท่านั้น ถ้าจะเปิดเว็บสาธารณะระยะยาว ควรเปลี่ยนเป็นรูปที่คุณมีสิทธิ์ใช้เอง

## ฟีเจอร์หลัก
- **หน้าแรก**: hero การ์ดซ้อนกัน, ช่องค้นหา, ตารางการ์ดที่กำลังประมูลพร้อมนับถอยหลัง, **ร้านค้าแนะนำ** ท้ายหน้า (ดูได้โดยไม่ต้องล็อกอิน)
- **หน้ารายละเอียด**: รูปการ์ด, ข้อมูลการ์ด (หมวดหมู่ รหัสการ์ด ระดับ สภาพ ผู้ขาย), ราคาปัจจุบัน, กล่องเสนอราคา, ประวัติการประมูล
- **กติกาขยายเวลา**: ประมูลในช่วง 5 นาทีสุดท้าย → ขยายเป็น 5 นาทีนับจากนั้น
- **ลงขายการ์ด**: กดเลือกรูปจากเครื่อง (มีพรีวิว) หรือเลือกไอคอนแทนถ้าไม่ใส่รูป, แก้ไข/เปลี่ยนรูปได้ตราบที่ยังไม่มีผู้ประมูล
- **หน้าร้าน** `/shop/{id}`: รวมการ์ดที่กำลังประมูลของผู้ขายแต่ละคน
- **โปรไฟล์** `/profile`: เปลี่ยน/ลบรูปโปรไฟล์ (ระบบครอปเป็นสี่เหลี่ยมจัตุรัส)
- **สมัครสมาชิก**: ใช้แค่ชื่อผู้ใช้กับรหัสผ่าน ไม่ต้องใช้อีเมล
- หน้าล็อกอิน/สมัครสมาชิกแบบแบ่งสองฝั่ง มีการ์ดโชว์
- ข้อมูลตัวอย่าง: 3 ร้านค้า (`napaksoy_shop`, `mewcorner`, `goldcard_th`) กับการ์ด 5 ใบ ลงให้อัตโนมัติตอนเริ่มระบบครั้งแรก (บัญชีร้านตัวอย่างใช้รหัสผ่านสุ่ม ล็อกอินเข้าไม่ได้)

## วิธีใช้งาน

**ผู้ใช้ทั่วไป (role: user)**
1. สมัครสมาชิกและเข้าสู่ระบบ
2. เลือกการ์ด ใส่ราคาประมูลในกล่องด้านขวา (ต้องไม่ต่ำกว่าขั้นต่ำที่แสดง)
3. เมนู "ลงขายการ์ด": เลือกรูป ใส่ชื่อ/รหัสการ์ด/ระดับ/สภาพ/ราคา และระยะเวลา (5 นาที – 7 วัน)
4. เมนูชื่อของคุณ (มุมขวาบน) → โปรไฟล์ เปลี่ยนรูปโปรไฟล์ได้
5. เมนู "ประมูลของฉัน": ดูสถานะ นำอยู่ / ถูกแซง / ชนะ

**ผู้ดูแลระบบ (role: admin)** — เมนู "ผู้ดูแลระบบ" (`/admin`): ดูสถิติ, ยกเลิก/ลบการประมูล, เปลี่ยนบทบาท/ลบสมาชิก, ดูประวัติการประมูลทั้งหมด

## ตรงตามเกณฑ์ขั้นต่ำ

| # | ข้อกำหนด | ทำไว้อย่างไร |
|---|---|---|
| 1 | สมัคร/เข้าสู่ระบบ + password hashing | `/register`, `/login` เก็บรหัสผ่านด้วย **bcrypt (cost 12)** มี salt ในตัว |
| 2 | อย่างน้อย 2 บทบาท | `user` และ `admin` ตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ทุกคำขอ user เข้า `/admin` ได้ 403 |
| 3 | CRUD ที่มีเจ้าของ | **รายการประมูล + รูปการ์ด**: ผู้ใช้ A แก้/ลบ/เปลี่ยนรูปของผู้ใช้ B ไม่ได้ เพราะ SQL ผูก `seller_id` จาก session |
| 4 | ฟอร์มอย่างน้อย 2 ฟอร์ม | (ก) ฟอร์มลงขายการ์ด (ข) ฟอร์มเสนอราคา (ค) ฟอร์มเปลี่ยนรูปโปรไฟล์ บันทึกลงฐานข้อมูลแล้วแสดงผลกลับ |
| 5 | หน้าผู้ดูแลระบบ | `/admin` |

## การป้องกันการโจมตี

| ภัยคุกคาม | วิธีป้องกันในโค้ด |
|---|---|
| รหัสผ่านรั่ว | bcrypt cost 12, นโยบายรหัสผ่านตอนสมัคร (≥8 ตัว มีตัวอักษร+ตัวเลข, ≤72 ไบต์) |
| SQL Injection | placeholder `?` ทุกคำสั่ง รวมถึงช่องค้นหา (escape `%` `_` ใน LIKE) |
| XSS | `html/template` escape ตามบริบท + CSP `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' blob:` ไม่มี inline script |
| CSRF | token สุ่มผูกกับ session ทุกฟอร์ม POST (เทียบแบบ constant-time) + ตรวจ `Sec-Fetch-Site` + cookie `SameSite=Lax` |
| **อัปโหลดไฟล์อันตราย** | จำกัด 2MB, ตรวจชนิดจากเนื้อไฟล์จริง (ไม่เชื่อนามสกุล/Content-Type), อนุญาตเฉพาะ JPEG/PNG/GIF, จำกัดกว้าง/ยาว ≤3000px กัน decompression bomb (อ่านขนาดจากหัวไฟล์ก่อน decode), **decode แล้ว encode เป็น JPEG ใหม่ทุกครั้ง** (ทิ้ง EXIF และข้อมูลแอบแฝง/polyglot), เก็บในฐานข้อมูลและเสิร์ฟด้วย id เท่านั้น (ไม่ใช้ชื่อไฟล์จากผู้ใช้ → ไม่มี path traversal), `nosniff`, อัปโหลดได้เฉพาะผู้ล็อกอินและเฉพาะ 3 เส้นทาง, rate limit |
| IDOR / แก้ข้อมูลคนอื่น | ตรวจความเป็นเจ้าของใน SQL, ไม่รับ `seller_id`/`user_id` จากฟอร์ม, ไม่ใช่เจ้าของตอบ 404, เปลี่ยนได้แค่รูปโปรไฟล์ของตัวเอง |
| ยกระดับสิทธิ์ / Mass assignment | `role` กำหนดที่เซิร์ฟเวอร์ (สมัครใหม่ = `user`), อ่าน role สดจาก DB ทุกคำขอ, แอดมินเปลี่ยน role/ลบบัญชีตัวเองไม่ได้ |
| **โกงการประมูล** | ตรวจกติกาทั้งหมดใน `UPDATE` เดียวแบบ atomic: ยังเปิดอยู่, ราคา ≥ ขั้นต่ำ, ผู้ขายประมูลเองไม่ได้, ผู้นำอยู่แล้วไม่ต้องประมูลซ้ำ → กดพร้อมกันหลายคนก็ไม่เกิดราคาซ้อนหรือประมูลหลังปิด |
| **สลับรูปหลอก** | เปลี่ยนรูป/แก้ไข/ลบการ์ดไม่ได้เมื่อมีผู้ประมูลแล้ว (บังคับด้วย `bid_count=0` ใน SQL) |
| ปลอมเวลา/ราคา | ใช้เวลาของเซิร์ฟเวอร์เท่านั้น (JS นับถอยหลังเป็นแค่การแสดงผล), ราคาเป็นจำนวนเต็มบาท จำกัดช่วงค่า |
| ค่าฟอร์มแปลกปลอม | ตัวเลือก (หมวด/ระดับ/สภาพ/ไอคอน/ระยะเวลา) ใช้ whitelist ฝั่งเซิร์ฟเวอร์ |
| Brute force / spam | rate limit ต่อ IP (login/สมัคร), ต่อผู้ใช้ (ลงขาย/ประมูล/อัปโหลด) + ล็อกบัญชี 15 นาทีเมื่อรหัสผิด 5 ครั้ง |
| User enumeration / timing | ข้อความ login ผิดเหมือนกันทุกกรณี + เทียบ bcrypt กับ dummy hash เมื่อไม่พบผู้ใช้ |
| Session hijack / fixation | token สุ่ม 256 บิต เก็บเฉพาะ SHA-256 ใน DB, cookie `HttpOnly`+`Secure`+`SameSite`+`__Host-`, หมุน session หลังล็อกอิน, หมดอายุ 12 ชม., ขอรูปภาพไม่สร้าง session |
| Clickjacking / MIME sniffing | `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy`, HSTS |
| DoS / ข้อมูลขนาดใหญ่ | จำกัด body 64KB (ฟอร์มปกติ) / 3MB (ฟอร์มแนบรูป), จำกัดความยาวทุกฟิลด์, timeout ของ server |
| ความเป็นส่วนตัว | ชื่อผู้ประมูลถูกซ่อนบางส่วนต่อสาธารณะ, ไม่เก็บอีเมล |
| ข้อมูลระบบรั่ว | error ภายในถูก log ฝั่งเซิร์ฟเวอร์ ผู้ใช้เห็นข้อความทั่วไป, `Cache-Control: no-store` |
| Container | รันแอปด้วยผู้ใช้ที่ไม่ใช่ root |

## รันในเครื่อง

ต้องมี Go 1.22 ขึ้นไป **ลบไฟล์ `app.db*` ทุกครั้งที่เปลี่ยนเวอร์ชัน** เพราะโครงตารางเปลี่ยน (เวอร์ชันนี้ตัดอีเมลออกและเพิ่มตารางรูป)

```powershell
cd C:\clubboard
Remove-Item app.db*
go mod tidy
$env:ADMIN_USERNAME="admin"
$env:ADMIN_PASSWORD="12345"
go run .
```

เปิด http://localhost:8080

> **คำเตือนเรื่องรหัสแอดมิน:** `12345` ใช้ทดสอบในเครื่องได้ (ระบบแสดงคำเตือนตอนเริ่ม) แต่ **ห้ามใช้บนเซิร์ฟเวอร์จริง** เพราะเดาได้ในครั้งเดียว และแอดมินลบข้อมูลทั้งระบบได้ ตอน deploy ให้ตั้งรหัสที่แข็งแรงด้วย `fly secrets set`

| ตัวแปร | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `PORT` | `8080` | พอร์ตที่ฟัง |
| `DB_PATH` | `app.db` | ตำแหน่งไฟล์ SQLite (รูปทั้งหมดอยู่ในไฟล์นี้ด้วย) |
| `COOKIE_SECURE` | `false` | ตั้ง `true` เมื่อใช้ HTTPS |
| `TRUST_PROXY` | `false` | ตั้ง `true` เมื่ออยู่หลัง proxy ของโฮสต์ |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | – | สร้างแอดมินตอนเริ่มระบบ (ไม่มีรหัสผ่านฝังในโค้ด) |

## ทดสอบให้ครบเกณฑ์
1. สมัคร `user1` และ `user2` (คนที่สองใช้หน้าต่าง incognito) ดูว่าสมัครได้โดยไม่ต้องใช้อีเมล
2. `user1` ลงขายการ์ดพร้อมเลือกรูป ระยะเวลา "5 นาที (ไว้ทดสอบ)" แล้วลองแก้ไข/เปลี่ยนรูป
3. `user2` ประมูล ดูว่าราคาและประวัติอัปเดต ลองประมูลต่ำกว่าขั้นต่ำ (ต้องถูกปฏิเสธ)
4. `user1` ลองประมูลการ์ดตัวเอง และลองแก้การ์ดหลังมีคนประมูลแล้ว (ต้องถูกปฏิเสธ)
5. ประมูลในช่วง 5 นาทีสุดท้าย ดูว่านับถอยหลังขยายเป็น 5 นาที
6. ไปที่ "โปรไฟล์" เปลี่ยนรูปโปรไฟล์ ดูว่ารูปขึ้นที่เมนูและหน้าร้าน
7. ลองอัปโหลดไฟล์ที่ไม่ใช่รูป (เช่นเปลี่ยนนามสกุล .txt เป็น .jpg) ต้องถูกปฏิเสธ
8. ล็อกอิน `admin` → `/admin` ลองยกเลิกการประมูล; ล็อกอินเป็น user แล้วพิมพ์ `/admin` ควรได้ 403

## ชุดคำถามที่อาจโดนถามตอนนำเสนอ

1. **ทำไมใช้ bcrypt ไม่ใช้ SHA-256/MD5?** แฮชทั่วไปเร็วเกินไป เดารหัสได้เป็นพันล้านครั้ง/วินาที bcrypt ตั้งใจให้ช้า ปรับ cost ได้ และมี salt ต่อรหัสผ่าน
2. **การอัปโหลดรูปอันตรายอย่างไร และกันอย่างไร?** ผู้โจมตีอาจแนบสคริปต์ในไฟล์ปลอมเป็นรูป หรือส่งไฟล์ใหญ่ผิดปกติ เรากัน 5 ชั้น: จำกัดขนาด, ตรวจชนิดจากเนื้อไฟล์จริง, จำกัดความกว้างยาว, decode แล้ว encode ใหม่ (เหลือแต่พิกเซล), เสิร์ฟด้วย id พร้อม `nosniff` ไม่ใช้ชื่อไฟล์จากผู้ใช้
3. **ทำไมเก็บรูปในฐานข้อมูลไม่เก็บเป็นไฟล์?** ควบคุมสิทธิ์ง่าย ไม่มีพาธจากผู้ใช้ จึงไม่มี path traversal และสำรองข้อมูลทีเดียวไฟล์เดียว (ข้อเสีย: ฐานข้อมูลใหญ่ขึ้น ถ้าระบบโตควรย้ายไป object storage)
4. **ถ้าสองคนกดประมูลพร้อมกันจะเกิดอะไร?** กติกาตรวจใน `UPDATE` คำสั่งเดียวแบบ atomic ภายใน transaction คนที่มาทีหลังจะไม่ผ่านเงื่อนไขราคาขั้นต่ำและถูกปฏิเสธ
5. **ถ้าผู้ใช้แก้นาฬิกาเครื่อง หรือแก้ JavaScript จะประมูลหลังปิดได้ไหม?** ไม่ได้ เซิร์ฟเวอร์ตัดสินด้วยเวลาของตัวเอง JS นับถอยหลังเป็นแค่การแสดงผล
6. **ผู้ใช้ A แก้/ลบ/เปลี่ยนรูปการ์ดของ B ได้ไหม?** ไม่ได้ SQL ผูก `seller_id` จาก session ลองยิง `POST /auctions/<id ของ B>/edit` จะได้ 404
7. **ทำไมเปลี่ยนรูปหลังมีคนประมูลไม่ได้?** กันผู้ขายสลับรูปหลอกคนที่เสนอราคาไปแล้ว บังคับด้วย `bid_count=0` ใน SQL
8. **ทำไมเก็บราคาเป็นจำนวนเต็ม?** เลี่ยงปัญหาปัดเศษของทศนิยม
9. **กติกาขยายเวลา (anti-sniping) คืออะไร?** กันคนมาประมูลในวินาทีสุดท้ายจนคนอื่นตอบโต้ไม่ทัน
10. **CSRF คืออะไร กันอย่างไร?** เว็บอื่นหลอกให้เบราว์เซอร์ส่งคำขอพร้อม cookie ของเรา กันด้วย token ผูก session ร่วมกับ SameSite และ Fetch Metadata
11. **XSS กับ SQL Injection ต่างกันอย่างไร?** XSS แทรกสคริปต์ฝั่งเบราว์เซอร์ (กันด้วย auto-escape + CSP) ส่วน SQLi แทรกคำสั่งฐานข้อมูล (กันด้วย placeholder)
12. **ทำไมไม่ใช้อีเมลสมัคร?** ลดข้อมูลส่วนบุคคลที่ต้องเก็บ (data minimization) ข้อจำกัดคือกู้รหัสผ่านทางอีเมลไม่ได้
13. **ข้อจำกัด/ที่ปรับปรุงต่อได้** ยังไม่มีระบบชำระเงิน/ที่อยู่จัดส่ง, ไม่มีรีเซ็ตรหัสผ่าน/2FA, ผลการประมูลอัปเดตเมื่อรีเฟรช (ยังไม่ใช้ WebSocket), rate limit เก็บใน memory (หลายเครื่องควรใช้ Redis), SQLite เหมาะกับเครื่องเดียว
